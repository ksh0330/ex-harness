# 1차 호출: README 분석과 질문 설계
1. README, 과제 안내, 제출물 명세를 읽는다. 기존 코드는 파일 트리 2단계와 진입점만 본다.
2. README 내용을 세 칸으로 나눈다: 확인된 사실 / 검증 안 된 가정 / 이미 적힌 해법 제안.
3. 업무 담당자에게 물을 질문을 아래 순서로 단계당 1~2개, 총 8개 이하로 만든다.
   해법 단어(앱, 기능, AI, 자동화 등)를 질문에 넣지 않는다. 문제를 듣는 질문만 한다.
   - 에피소드: 최근에 이 문제가 실제로 터진 사례 하나
   - 워크어라운드: 지금은 어떻게 버티고 있는지, 무엇이 불편한지
   - 정량화: 빈도, 걸리는 시간, 비용, 지금 수치와 원하는 수치
   - 당사자: 누가 쓰고, 누가 결정하고, 누가 유지하는지
   - 경계: 절대 하면 안 되는 것, 제약, 기한, 포기해도 되는 것
4. README가 문제와 해법을 이미 자세히 적고 있으면 질문을 정량화와 경계 위주 4개로 줄인다.
5. 출력: 세 칸 분석 요약과 질문 목록. 파일은 아직 쓰지 않는다.

# 2차 호출: 내가 실무자 답변 요약을 주면
1. docs/DISCOVERY.md를 작성한다.
   - 실무자 발언 요지 (질문별 한 줄)
   - 렌즈별 관찰: 병목, 리드타임, 비용, 수요 변동, 위험(보안, 개인정보), 운영 유지
   - 근본 문제 후보 2~3개와 각각의 근거
   - 가장 큰 간극 하나 추천, 이유, 측정 가능한 지표 후보
   - 3 why 답: 데이터 원천, 안 풀면 비싼 것, 유지 주체
2. 15줄 이내로 요약 보고하고 내 결정을 기다린다. docs/STATUS.md 작업 로그에 한 줄 추가.
