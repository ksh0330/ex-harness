# ex-harness

SK하이닉스 AI 해커톤 2026 2차 예선(Cofa Probe, Codex)용 개인 작업 하네스.
과제 답이나 결과물 코드는 없고, AI에게 일을 맡기고 검증하는 **작업 방식 지침과 스킬**만 담았다.
이 저장소는 2차 예선 결과 통지 전까지 공개 상태를 유지한다.

---

## 0. 외울 것은 이 한 줄

과제 작업 폴더 루트의 터미널에서:

```bash
git clone https://github.com/ksh0330/ex-harness /tmp/h && bash /tmp/h/install.sh
```

설치되는 것: `AGENTS.md`(과제 것이 있으면 뒤에 덧붙임), `.agents/skills/` 스킬 8개, `docs/STATUS.md`, `.harness/GUIDE.md`(이 문서).
이 문서를 시험 중 다시 보려면 새 터미널 탭에서 `less .harness/GUIDE.md` (q로 종료).

## 1. Codex 기본 조작

| 하고 싶은 것 | 입력 |
|---|---|
| Codex 시작 | `codex` |
| 모델, 권한 확인 | `/status` |
| 모델과 reasoning effort 변경 | `/model` (기본 6.1 Sol + medium, 막힐 때만 high, max와 ultra 금지) |
| 스킬 목록 | `/skills` |
| 스킬 실행 | `$discover` 처럼 `$스킬이름` (안 되면 아래 "스킬이 안 보일 때") |
| 명령 목록 전체 | `/` 만 입력 |
| 대화 압축 | `/compact` (가능하면 handoff 후 새 세션을 우선) |
| 새 세션 | `/new` 가 있으면 사용, 없으면 Codex 종료 후 `codex` 재실행 |
| 실행 중단 | `Esc` 또는 `Ctrl+C` (서버 터미널에서는 서버가 꺼짐) |
| 승인 요청 | 기다려도 진행 안 됨. 반드시 보고 승인 또는 거절 |

터미널 배치: 탭 1 `MAIN`(메인 Codex), 탭 2 `SERVER`(서버 실행, 절대 닫지 않기), 탭 3 `REVIEW`(교차 검증용 새 Codex). 탭 이름은 더블클릭으로 변경.

브라우저 미리보기: 서버를 `0.0.0.0`에 띄우고 왼쪽 Browser 도구에서 PORT와 경로 입력 후 원형 화살표.

## 2. 단계별 진행표 (10:00 시작 기준, 늦게 시작하면 그만큼 밀기)

| 시각 | 단계 | 내가 할 일 | Codex에 입력 |
|---|---|---|---|
| 10:00~10:05 | 감독 | 휴대폰 거치, 신분증, 안경 | |
| 10:05~10:08 | 설치 | 위 한 줄 실행, codex 실행, 모델 확인 | |
| 10:08~10:25 | **P1 발굴** | README 직접 정독. 실무자 DM으로 인터뷰 | `$discover` → 질문 받아서 실무자에게 묻기 → 답 요약을 Codex에 주며 `$discover 2차: (답변 요약)` |
| 10:25~10:35 | **P2 서면 합의** | 합의문 검토, 실무자에게 확인 메시지 보내기 | `$agreement` → 확인 후 `실무자 확인됨. 수정: ...` |
| | 교차 검증 | REVIEW 탭에서 새 codex | `$cross-review 대상: docs/AGREEMENT.md` |
| 10:35 | **인계 A** | | `$phase-gate` → `$handoff` → 새 세션에서 출력된 시작 문장 입력 |
| 10:35~10:50 | **P3 스캐폴딩** | 스택 결정, 실행 확인 | `$build-slice 스캐폴딩` |
| 10:50~11:40 | **P4 E2E v0** | 핵심 흐름 하나 끝까지. 브라우저로 직접 확인 | `$build-slice P0-1` 반복 |
| 11:40~11:50 | **P5 중간 검증** | 증거 표 확인, 남은 시간으로 범위 재조정 | `$verify` → `$phase-gate` |
| 11:50 | **인계 B** | | `$handoff` → 새 세션 |
| 11:50~12:30 | **P6 보강, 수용 확인** | P0 완성도, 엣지 케이스, 보안. P1은 여유 있을 때만 | `$build-slice ...` → 12:20쯤 `$verify` |
| **12:30** | **기능 동결** | 새 기능 금지 | REVIEW 탭: `$cross-review 대상: 코드 전체` |
| 12:30~12:45 | **P7 제출 의식** | 리뷰 지적 중 치명적인 것만 수정 | `$wrapup` → 화면에 나온 서술형 요약을 읽고 머리에 넣기 |
| **12:45~12:55** | **제출** | 저장 상태 확인 → "제출하고 문제풀기" → "제출물 확정하고 문제풀기" | |

시간 원칙: 질문 준비 화면은 최대 10분이고 재시도하면 다시 10분이다. **12:55 전에는 반드시 확정**한다.

README에 실무자의 문제와 해법이 이미 자세히 적혀 있으면 P1을 10분으로 줄이고, 정량화(현재 수치)와 경계(안 만들 것)만 확인한 뒤 넘어간다.

## 3. 실무자 인터뷰 순서 (해법 단어 금지)

1. **에피소드**: 최근에 이 문제 때문에 실제로 곤란했던 일 하나만 이야기해 주세요.
2. **워크어라운드**: 지금은 어떻게 처리하고 계세요? 그 방식에서 제일 번거로운 건?
3. **정량화**: 얼마나 자주, 한 번에 얼마나 걸리나요? 지금 수치와 원하는 수치는?
4. **당사자**: 누가 쓰고, 누가 결정하고, 만든 뒤 누가 관리하나요?
5. **경계**: 절대 하면 안 되는 것, 꼭 지켜야 할 제약, 시간 부족하면 포기해도 되는 건?

답에서 숫자(현재값)가 나오면 그대로 성공 기준의 "현재값"이 된다.

---

## 4. 세션 운영 규칙

- **메인 세션 하나**가 구현한다. 모델은 6.1 Sol medium.
- **REVIEW 탭**은 교차 검증 때만 새로 연다 (합의문 직후, 기능 동결 직후 두 번). 파일 수정 금지. 감시가 필요하면 6.0 Luna로 `$phase-gate`만 돌려도 된다.
- **인계 시점을 미리 고정**: 10:35(P2 끝), 11:50(P5 끝), 그리고 Codex 상태 표시의 컨텍스트 여유가 40% 미만일 때.
- 같은 파일을 메인과 REVIEW가 동시에 수정하지 않는다. 에디터에서 AI가 작업 중인 파일을 손으로 고치지 않는다.
- 같은 실패 2번이면 멈추고 가설부터. 이상한 루프에 토큰을 태우지 않는다.

---

## 5. 기본 스택 (과제 지정이 없을 때)

- 원칙: **프로세스 하나, 포트 하나, 저장소는 SQLite나 JSON 파일**. 미리보기와 인계가 쉬워진다.
- Python이 되면: FastAPI가 API와 정적 HTML을 함께 서빙. `uvicorn app:app --host 0.0.0.0 --port 8000`
- pip이 막혀 있으면: 표준 라이브러리 `http.server` + `sqlite3`만으로도 가능
- Node가 편하면: Express 하나가 API와 정적 파일 서빙. `app.listen(3000, '0.0.0.0')`
- 앱 안에 LLM 기능이 필요해도 개인 API 키는 금지. 판정과 저장은 코드로, LLM 부분은 없거나 실패해도 동작하는 대체 경로를 둔다.

## 7. clone이 안 될 때 (1분 넘게 막히면 바로 이 방법)

에디터에서 새 파일 `AGENTS.md`를 만들고 아래 10줄을 직접 입력한다 (외부 복사 불가하니 손으로).

```text
나는 PM, 너는 개발자. 과제 README가 최우선.
합의(docs/AGREEMENT.md) 전에는 구현하지 않는다.
큰 작업은 5줄 계획 먼저, 내 승인 후 실행. 한 번에 기능 하나.
요청 범위만 수정. 단순하게. 요청 안 한 기능과 추상화 금지.
완료 주장 전에 테스트나 실행을 새로 돌려 결과를 보여준다. 추측 금지.
판정, 계산, 저장은 코드와 테스트로 고정. LLM은 해석과 초안만.
서버는 0.0.0.0. push, Codex 업데이트, 설정 변경, 개인 API 키 금지.
커밋은 [P단계] 태그. docs/STATUS.md에 단계와 로그 기록.
결정은 docs/DECISIONS.md, 세션 교체 전 docs/HANDOFF.md 작성.
응답은 한국어로 짧게.
```

스킬 대신 쓸 짧은 지시:

| 스킬 | 말로 시키기 |
|---|---|
| discover | README를 사실, 가정, 해법으로 나누고 실무자 질문 8개 만들어. 해법 단어 금지, 에피소드 > 워크어라운드 > 정량화 > 당사자 > 경계 순 |
| agreement | docs/AGREEMENT.md 작성: 문제, 병목 하나, 성공 기준(지표, 목표, 현재값, 측정 위치), 만들 것, 안 만들 것, 제약 |
| build-slice | P0-1만: 계획 5줄, 승인 후 구현, 테스트 실행 결과, [P4] 커밋, STATUS 한 줄 |
| verify | 성공 기준별 충족/부분/미충족을 지금 실행한 증거(파일:줄, 테스트, 명령)와 함께 표로 |
| phase-gate | 드리프트, 증거 없는 체크, 너무 순조로운 곳을 감사하고 시간 대비 진척 판단 |
| handoff | docs/HANDOFF.md: 목표, 현재 단계, 완료(증거), 진행 중, 다음 할 일, 실행법, 결정, 함정, 하지 말 것 |
| cross-review | 파일 수정 없이 요구사항, 버그, 보안, 유지보수, 문서와 코드 불일치 상위 5개를 파일:줄과 함께 |
| wrapup | 필수 파일, 실행 재확인, README 정리, 최종 handoff, 화면에 약점 5개(지점 > 위험 > 개선 계획) |

## 8. 후속 서술형 (6문항, 문항당 5분, AI 금지, 복사 불가)

답 틀: **결론 한 줄 → 근거(파일, 함수, 결정 이유) → 어떻게 검증했나 → 약점과 다음 계획**

- "왜 이렇게 만들었나": 합의된 병목과 성공 기준에서 출발해 설명, 버린 대안 하나 언급
- "장애가 나면": 어디서(파일, 경계) 어떤 증상이 나는지, 무엇을 먼저 확인할지, 어떻게 복구할지
- "약점은": 약점 지점 지목 → 왜 위험한가와 파급 → 다음에 무엇을 검증하고 개선할지
- 질문 전제가 실제 구현과 다르면 그 차이를 먼저 밝힌다
- 시간이 끝나면 자동 확정, 이전 문항으로 못 돌아감. 한 문항에 매달리지 않는다
