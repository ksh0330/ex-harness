# 프로젝트 시작 지침

과제 README·지정 산출물·기존 AGENTS.md가 우선이다. 현재 폴더·Git 상태·관련 진입점과 실행 파일을 확인하고 프로젝트 분석부터 시작한다. 설치 파일의 존재를 Skill 활성화로 간주하지 않는다.

큰 작업은 아래 P1~P7 흐름을 관리하되 작은 수정에 빈 단계·문서·커밋을 만들지 않는다. 권한 내 다음 작업은 계속 수행한다. 실제 사용자 결정·현장 조작이 필요한 지점에만 멈춘다.

| 단계 | 할 일 | 주로 읽을 Skill |
|---|---|---|
| P1 탐색 | README·제출 형식·제약·데이터 원천·유지 주체 확인. 결과를 바꾸는 실무자 질문 초안 | discover |
| P2 범위 | 데이터 구조·역할/권한·시스템 흐름·필수/제외·성공 기준·기준 알고리즘 결정 | agreement |
| P3 골격 | 기존 스택으로 최소 실행 흐름 구성·실행 | build-slice |
| P4 구현 | 필수 기능을 흐름별 구현·관련 테스트 | build-slice |
| P5 검증 | 단위·통합·빈 값/잘못된 입력/중복/경계·인증/역할별 권한·저장/조회·데이터 정합성·회귀 | verify |
| P6 보강 | 실패 수정·기준 알고리즘과 대안 비교·가능하면 실측. 실제 UI 핵심 흐름·예외 메시지·반응형 확인 | verify, 필요한 경우 cross-review |
| P7 전달 | 지정 산출물·README 명령 재실행·AI 협업/결정 기록·파일/용량·한계·구조 설명·사용자 최종 제출 | wrapup, handoff |

단계 전환에는 phase-gate로 실제 완료·새로 실행한 검증과 종료 코드·미완료·중요 결정·변경 파일/Git 상태·로컬 커밋 가능 여부·다음 조건을 STATUS에 기록한다. P3 이전에도 의미 있는 검증 산출물이 있으면 커밋한다. 현장 Git 사용이 허용되고 사용자가 금지하지 않았으면 이번 검증된 변경만 경로를 명시해 stage하고 `[P단계] 내용`으로 로컬 커밋한다. 기존 사용자 변경과 실패 코드는 섞지 않는다. Git 저장소가 없으면 init 전에 질문한다. push·Git identity 변경은 하지 않는다.

중요 선택은 문제·대안·추천과 근거·다른 대안의 비용·필요 결정을 짧게 제시한다. DECISIONS에 AI 제안 / 사용자 수락·거절·수정·미응답을 구분해 기록한다. 단순 위임 구현을 반복 승인받지 않는다. 실무자 질문은 초안만 작성하고 사용자가 실제 받은 답변만 반영한다.

Skill A: 목록에서 인식되면 해당 단계에 사용한다. B: 파일만 있으면 해당 SKILL.md를 직접 읽는다. C: 설치 실패·이름 충돌이면 원본 하네스 `skills/<이름>/SKILL.md`를 읽고, 그것도 안 되면 이 지침으로 진행한다. Hook·MCP·Plugin·별도 에이전트는 필요 없다.

Skill 호출을 사용자에게 매번 요구하지 않는다. 설치본은 `.agents/skills/<이름>/SKILL.md`다. 기존 `.harness` 지침이 원본과 다르면 덮어쓰지 않고 시작 프로그램이 안내한 원본을 보조로 읽는다. Hook이 없거나 실패해도 phase-gate의 검증 결과·Git 상태·결정·로컬 커밋·다음 작업·최종 제출 점검을 직접 수행한다. Hook은 제공 버전의 실제 지원과 현장 허용이 모두 확인되고 사용자가 선택했을 때만 별도 검토하며 신뢰/승인 설정을 우회하지 않는다.

긴 입력은 플랫폼 IDE 편집기의 Markdown(예: `notes/INPUT.md`, `notes/STAKEHOLDER.md`)에 저장하고 Codex 채팅에 `notes/INPUT.md를 읽고 반영해`라고 짧게 입력한다. DM은 출처·수신 여부를 분리하고 답변이 없으면 미확인으로 남긴다. 키·인증정보를 저장하거나 과제 자료를 외부 전송하지 않는다.

실제 DM 응답으로 요구사항이 바뀌면 변경 전/후와 출처 → 코드·데이터·수용 기준 영향 → 기존 구현/diff 보존 → 필요한 부분만 수정 → 관련 회귀 → 결정 기록·검증된 파일의 로컬 커밋 순으로 처리한다. 삭제/마이그레이션 등 새 권한이 필요한 부분만 묻는다. DM 초안 작성과 플랫폼 내부 전송은 구분하며 전송은 사용자가 한다.

질문은 실무자만 아는 조건·범위를 바꾸는 선택·알고리즘/제약 충돌·새 권한·실행 승인/화면 관찰·세션 조작/최종 제출에 한정한다. 결과가 달라지는 경우에만 아래 형식을 쓰고, 답변 즉시 결정 로그에 반영한다. 필수 답변을 기다리는 동안 독립적인 허용 작업은 계속한다.

```text
결정 필요:
상황: 문제와 영향
A: 선택지·장단점
B: 선택지·장단점
추천: 선택과 근거
답변: A / B / 수정안
```

메인 세션 하나가 기본이다. 부족하면 현재 유지·`/compact`·`codex resume`·새 세션·허용된 읽기 전용 리뷰 중 선택한다. 전환 전 HANDOFF와 Git 상태를 보존하고 실제 과제 폴더 터미널에서 입력할 명령과 새 채팅에 읽힐 문서를 안내한다. 상태가 자동 공유된다고 가정하거나 같은 파일을 동시 편집하지 않는다.

UI가 있으면 제공 미리보기에서 실제 입력→처리→저장→새로고침·오류·좁은 화면을 확인한다. 직접 조작 불가 시 사용자에게 주소·포트·조작·기대 결과를 안내하고 관찰 전 미검증으로 남긴다. Computer Use나 외부 브라우저 연결을 기본 활성화하지 않는다. UI 없는 과제는 해당 없음이다. 최적화는 구현 완료와 구분하고 같은 입력의 정확성·성능을 비교한다. 시간이 부족하면 필수 기능과 데이터 안정성을 우선한다.

P1에서 현장 타이머·제출 경로·제한을 읽고, 단계 전환 때 실제 남은 시간에 맞춰 선택 기능을 줄인다. 시간이 없으면 질문/문서 분량도 줄이되 필수 기능·데이터·검증 증거·제출물 보존은 유지한다. 한 기능의 성공을 전체 완료로 표시하지 않는다. 현재 사용자 제공 재시험 안내는 코딩 최대 180분·서술형 30분·최종 23:00 종료, RAM 16GB·제출 10GB 이하이며 현장 최신 안내가 우선이다. 시작 시간을 추측하거나 서술형 시간을 코딩에 사용하지 않는다. 서술형 시작 후 AI 사용·복사 붙여넣기를 안내하지 않는다.

P7에서 제출 파일 목록·실제 총용량·필수 경로를 확인한다. 과제 폴더 안 `ex-harness/`에는 원본과 내부 `.git`도 있다. `.gitignore`는 폴더 전체 제출에서 제외해 주지 않는다. 원본·의존성·DB·사용자 파일을 임의 삭제하지 말고 지정 제출 방식에 맞춰 필요한 범위를 구분한다. 최종 제출 버튼/전송은 사용자에게 남긴다.
