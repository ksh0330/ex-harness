# 35분 모의시험 두 가지

두 과제는 합성 연습이다. 실제 시험 문제·답안을 예측하지 않는다.
웹 기존 시스템 확장과 비웹 데이터 연계를 번갈아 연습한다. 둘 다 한 번에 할 필요는 없다.
이 문서는 진행 대본이며 사용자의 실제 수행 결과는 아직 기록되지 않았다.

## 준비: 원본과 분리

하네스 원본 루트의 Bash에서 로컬 연습 폴더를 만든다. 기존 폴더가 있으면 새 이름을 고른다.

```bash
python tools/install.py --target ../fde-practice --with-examples
python tools/install.py --target ../fde-practice --with-examples --apply
cd ../fde-practice/.harness/kit
```

설치된 kit는 연습 코드이며 원본과 별개다. 원본의 tests는 복사하지 않으므로 연습 과제에서 필요한 테스트를 작성한다.
저장소에 이미 연결된 과제에서 연습한다면 기존 Git 상태를 먼저 기록한다. 원본과 사용자 파일을 덮어쓰지 않는다.
Python이 없다면 설치·실행 실습은 미검증으로 남기고 직접 지시와 PM 결정 연습만 한다.

## 공통 진행표

| 분 | 과정 | PM이 직접 할 결정 | Codex의 역할·남길 증거 |
|---|---|---|---|
| 0~3 | 과제 README 확인·기존 코드 탐색 | 선택한 과제·제약 확인 | 사실·가정·진입점, git 상태 또는 원본 분리 확인 |
| 3~6 | 문제 정의·실무자 질문 | 역할 카드로 답하고 모르는 수치는 미확인 | 결과를 바꾸는 질문만, 데이터·실패 비용·유지 담당 정리 |
| 6~9 | 범위·수용 기준·기술 선택 | 필수/제외를 직접 결정 | 기존 코어 재사용과 어댑터 변경 범위, 기준별 테스트 계획 |
| 9~18 | AI 구현 위임·실행 | 중간 출력과 실제 입력 확인 | 재현/새 기준의 실패 테스트 → 작은 수정 → 관련 테스트·실행 |
| 18~21 | 예상치 못한 문제 | 아래 사건 카드 한 개 선택 | 현재 상태 보존, 원인·영향 분석. 성공 기준을 몰래 바꾸지 않음 |
| 21~25 | 사용자 개입·방향 수정·재개 | 남은 시간의 우선순위·포기할 항목 결정 | 영향 파일만 변경·관련 회귀 테스트. 선택 기능 확대 중단 |
| 25~28 | Handoff | 현재 세션 지속 또는 새 세션을 선택 | 실제 파일·성공/실패·다음 명령·함정을 HANDOFF에 기록 |
| 28~32 | 최종 검증·결과 대조 | 수용/보류와 미검증 확인 | 실행 명령·종료 코드, 기준별 증거 표. 기능 추가 금지 |
| 32~35 | 구조·약점 설명 | AI 도움 없이 90초 설명·질문 두 개 답하기 | 설명이 코드와 맞는지 근거 제공. 학습 완료 대리 판정 금지 |

타이머가 끝나면 미완료를 그대로 남긴다. “모두 완료” 대신 실제 통과·미검증을 구분한다.

## A. 동네 수리 접수: 웹 서비스 확장

과제: [repair-status README](../examples/tasks/repair-status.md).

PM이 아래 카드의 담당자 역할로 답한다. 이 대화는 **가상 인터뷰**이며 실제 실무자 확인으로 기록하지 않는다.

<details><summary>실무자 역할 카드</summary>

전화 응대 중 접수 번호 하나의 상태만 빨리 확인하고 싶다. 전화 수·현재 소요 시간은 측정하지 않았다.
이름·전화번호는 이번 연습에 저장하지 않는다. 기존 수리 담당자가 유지한다.
새 화면이 꼭 필요한지는 PM이 결정한다. 시간 부족 시 UI를 미루고 API·오류 처리를 먼저 확인해도 된다.

</details>

PM 결정 질문: 단건 API만 필수로 할까, 번호 입력 화면도 필수로 할까? 없는 번호·잘못된 번호의 결과는 무엇인가?
선택 예시: `GET /api/items/1`은 해당 레코드, 존재하지 않는 번호는 404, 기존 생성·검색·상태 갱신 유지. 이는 연습용 제안이며 PM이 최종 선택한다.

Codex 위임 문장:

```text
examples/tasks/repair-status.md와 기존 코드를 읽어. 나는 PM이다.
먼저 필요한 질문과 최소 변경·검증 계획을 제시해. 내가 필수 범위를 정하면 그 흐름을 구현해.
수치·실무자 확인을 만들지 말고 기존 코어와 포트를 재사용해.
```

검증 후보: 번호 1 등록 후 단건 조회, 없는 번호, 기존 검색·완료 전환. 테스트 서버는 종료하고 지속 서버는 PM 터미널에서 실행한다.

사건 카드 중 하나를 PM이 선택한다.

- `8000 포트가 사용 중이다.` 기존 프로세스를 임의 종료하지 않고 본인의 기존 서버인지 확인, 필요하면 허용된 포트 하나로 실행·미리보기·문서를 함께 맞춘다.
- `브라우저 미리보기가 열리지 않는다.` 바인딩·실제 포트·/health를 확인한다. HTTP 검증만 했다면 UI 검증은 보류로 남긴다.
- `추가 화면 구현이 지연된다.` PM이 API만 남길지 결정하고 이미 한 변경을 파악한 뒤 영향 범위만 줄인다.

최종 설명 질문: 왜 Store를 HTTP handler 안에 복제하지 않았나? 이 API를 외부 공개하려면 무엇이 부족한가?

## B. 지역 자료 보관: 비웹 CSV 연계·회귀 수정

과제: [archive-intake README](../examples/tasks/archive-intake.md).

<details><summary>실무자 역할 카드</summary>

공급자가 pending을 queued와 같은 의미로 사용한다. 나머지 임의 상태를 허용해 달라는 요청은 아니다.
공급 CSV를 수정해서 다시 보내 달라고 하면 다음 날까지 지연될 수 있으나 실제 지연 비용은 미측정이다.
기존 queued 입력은 계속 들어온다. 모르는 단계는 전체 거부하고 원본 파일을 유지해야 한다.
중복 import 처리와 자동 시간 예약은 PM이 별도 결정할 일이다.

</details>

PM 결정 질문: pending만 별칭으로 허용할까, 전체 단계 규칙을 바꿀까? 이번에는 중복 제거를 추가할까, 사용상 주의로 남길까?
일반적인 작은 범위: 어댑터의 외부 값 매핑만 추가하고 공통 상태 세 개와 거부 정책은 유지한다. PM이 결정한 뒤 진행한다.

Codex 입력:

```text
examples/tasks/archive-intake.md를 읽고 pending 입력의 실패를 먼저 재현해.
질문 후 내가 호환 범위를 결정하면 해당 경계만 수정해.
신규 입력, 기존 queued 입력, 잘못된 후반 행의 전체 거부·기존 DB 보존을 실제 CLI와 테스트로 확인해.
```

필수 실행 후보:

```bash
python -m examples.batch import pending.csv --db .run/practice.sqlite3
python -m examples.batch export --db .run/practice.sqlite3
```

`pending.csv`는 과제 README의 합성 데이터를 연습 폴더에 직접 작성한다. 첫 실행의 실제 오류를 기록하고 수정 후 새로 실행한다.
빈 파일·잘못된 헤더·알 수 없는 stage를 추가해 거부와 데이터 보존을 확인한다. 같은 DB에 정상 파일을 여러 번 넣으면 중복이 생긴다는 현재 한계도 확인한다.

사건 카드:

- `같은 파일을 다시 넣어 행 수가 늘었다.` PM이 중복 제거를 이번 필수로 바꿀지, 문서화하고 새 테스트 DB로 검증할지 결정한다. DB를 몰래 지우지 않는다.
- `--output의 보고서가 이미 있다.` 기존 파일 보존을 확인하고 새 이름을 사용한다. 덮어쓰기 기능을 즉석 추가하지 않는다.
- `중간에 요구가 변경됐다: 모르는 상태는 건너뛰자.` 부분 반영이 데이터 신뢰에 미치는 영향과 기존 기준 변경을 설명한다. PM 결정 전 원자성 요구를 지우지 않는다.

최종 설명 질문: 왜 pending은 DB 상태가 아니라 어댑터의 매핑으로 처리했나? import와 export 둘을 한 원자 작업이라고 말할 수 있나?

통과를 AI가 대신 정하지 않는다. PM이 직접 명령·결과를 확인하고 설명할 수 있으면 해당 항목에 확인을 남긴다.
